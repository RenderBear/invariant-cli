The mechanical model

How Invariant works

It gives an agent room to change code, but makes it prove the finished snapshot still preserves the decisions your repository relies on.

The causal clock

Git order matters. Wall-clock time does not.

main       A──B──C
                ╲
work             D──E

candidate  A──B──C──M
                   ↑
              verify M
              then move main
A commit is a snapshot. Git knows which earlier snapshot it came from.
A branch is a pointer. Landing moves main from C to verified snapshot M.
Compare-and-swap prevents local ref races. If main moved inside this clone after M was built, landing stops and rebuilds from the new head.

Words worth knowing

A tiny glossary

Reach

How far a change reaches: local, bounded by accepted meaning, open for adoption, or gated because it rewrites what was accepted.

Domain

A stable responsibility such as “job delivery” or “tenant isolation.” It points to relevant architecture and contracts; it is not a folder.

Contract

A behavior one domain relies on another domain to preserve, paired with an executable check.

Discovery

A tracked question or finding. It warns while pending, but gains authority only if promoted into architecture, a domain, or a contract.

Exact tree

The precise set and contents of files that would exist after landing—not merely the agent’s branch before it meets the latest main.

Procedure

  1. Resolve the integration target once, then capture the request’s outcomes, paths, interfaces, and likely domains.
  2. Compute reach, load only the applicable domain rows, architecture anchors, contracts, and discovery warnings, then retain their governance digest.
  3. Apply the durable-meaning test and label the posture local, bounded, open, or gated.
  4. Open a reusable receipt; before the first mutation, create a generated invariant/work/<uuid> branch from the captured head.
  5. Before landing, recompute scope from the exact diff and hand the boundary decision, checks, domains, and architecture reviews to invariant task finish.

Semantic responsibility

Domain selection follows responsibilities and relied-on behavior, never directory names. The key question is whether a future locally reasonable change could become systemically wrong without knowing what this change decided. If not, no-record is explicit and valid. If meaning is uncertain, the brief routes to an audit; if authority is already clear, it routes directly to recording.

Git mechanics

The captured integration commit is the causal ground. A receipt under .invariant/runtime/briefs/ caches hashes, scope, target, and digest—but carries no authority. It survives an unrelated mergeable head advance, and becomes stale when governing content changes, scope expands, or the work branch conflicts.

read: HEAD + .invariant governance → write: disposable receipt → branch: invariant/work/<uuid>

invariant evidence Discovery · only when meaning is uncertain Creates bounded, causal evidence without making that evidence authoritative. +

Procedure

  1. Choose a scoped audit from the current work; a repository-wide audit happens only when explicitly requested.
  2. Record the inspected semantic scope, paths, ground commit, exact tree, evidence, and bounded findings.
  3. Classify each finding as adoptable, needing authority, needing a verifier, discovery-only, or no action.
  4. Resolve or discard facts that can be settled now. Queue a discovery only when an unresolved question is worth carrying forward.
  5. Close with one transition: no record, record ready, resolution required, or verifier required.

Semantic responsibility

An audit says “this is what the evidence suggests,” not “the repository must now obey this.” Existing code and history are evidence, never normative authority. A finding gains force only after authorized promotion into a domain responsibility, architecture decision, or executable contract.

Git mechanics

Audits and discoveries are tracked files under .invariant/. Their freshness is causal: Git ancestry must still contain the recorded ground, and later changes must not intersect the evidence they relied on. Timestamps do not decide validity. The evidence is committed and landed through the same isolated branch path as other repository changes.

write: .invariant/audits/<id>.yml [+ discoveries] · fresh = ancestor(ground) + no intersecting evidence change

invariant governance Adoption · before dependent work diverges Turns an authorized decision into durable, routable, verifiable repository meaning. +

Procedure

  1. Start from a direct authoritative instruction or a fresh audit/discovery and resolve any required human authority.
  2. Put rationale and non-executable decisions in an anchored architecture section.
  3. Change only the smallest domain responsibilities and pointers needed for routing; add contract metadata only for a relied-on cross-domain promise.
  4. Require executable evidence for every contract and resolve a promoted discovery in the same change.
  5. Validate all Invariant state, run affected verifiers, review architecture semantically, then recompile the brief before dependent work proceeds.

Semantic responsibility

Domains are retrieval indexes for stable responsibilities. Architecture owns the “why” and the non-executable boundary. Contracts protect behavior that at least two domains rely on. Records preserve operational meaning—ownership, recovery, compatibility, transactionality—not incidental technology choices. Existing records are amended in preference to creating competing truths.

Git mechanics

The skill edits versioned governance and defining Markdown on the work branch, alongside the implementation it governs. IDs and anchors are stable history keys; renaming one is a migration that must update every live reference while history remains immutable. Changes stay unstaged unless the invoking task owns landing, and the final candidate carries governance and code together.

write: .invariant/DOMAINS.yml · .invariant/CONTRACTS.yml · anchored Markdown · validate before candidate construction

invariant coordinate Execution · parallel or handoff-sensitive work only Makes concurrent ownership explicit with a dependency graph and causal leases. +

Procedure

  1. Activate only for independently verifiable parallel units, distinct owners, provider-before-consumer work, or a durable handoff.
  2. Define a plan with objectives, dependencies, path/interface/governance claims, provided and relied-on contracts, and a verifier for every unit.
  3. Validate the plan as a DAG and reject conflicting unordered claims or consumers that can run before their provider.
  4. Dispatch work branches and linked worktrees just in time, then mint a lease containing the unit’s exact ground and claims.
  5. Recheck lease freshness before accepting work; release landed units and remove the plan only when complete.

Semantic responsibility

Coordination grants temporary ownership, never truth. Sharing a domain is not automatically a collision; unordered overlap in paths, interfaces, or governance is. Dependencies express semantic ordering such as “define the protocol before implementing its consumer.” Plans deliberately contain no mutable progress field.

Git mechanics

Generated task branches use linked worktrees starting at the captured integration ground. Ignored runtime state lives in the primary worktree so all linked worktrees see the same leases. A lease binds owner, branch, worktree, target, ground, causal tip, digest, and claims. An intersecting landing makes it stale; expiry merely schedules a liveness check.

ignored: .invariant/runtime/{briefs,tasks,history,verifications,plans,leases,worktrees}/ · landed state: first-parent Invariant-Unit trailers · freshness: ancestry + claims

invariant task finish Convergence · every repository mutation Constructs, reviews, verifies, and atomically publishes the prospective Git tree. +

Procedure

  1. Capture the current integration head and construct the merge candidate without moving that branch.
  2. From the candidate’s exact diff, recompute reach, flag new topology, and require exactly one boundary disposition: no-record, a conclusive fresh audit, or recorded governance references.
  3. Validate Invariant state and derived scopes; review every affected architecture pointer and run all selected contract and repository checks.
  4. Authenticate any coordinated leases against their branches, target, and combined claims.
  5. Atomically move the target only if it still equals the captured head, then release completed runtime state.

Semantic responsibility

Landing never invents governance. It demands an explicit answer to “who owns the durable meaning in this tree?” Architecture is reviewed by judgment; contracts are checked executably. The candidate records the answer in Invariant-Boundary, Invariant-Governance, and Invariant-Architecture trailers. A later attested landing can cover an intervening first-parent range without rewriting history.

Git mechanics

Normal landing creates a dangling merge candidate and checks it out in a detached worktree. The target ref is untouched throughout validation. A compare-and-swap updates it from the captured object ID to the verified candidate ID; if another landing advanced the ref, the update fails and the candidate must be rebuilt. Direct landing exists only for an unborn target branch.

candidate M = merge(captured target C, work tip) → verify tree(M) → update-ref target M C

Why “exact tree” matters

Tests run after the work meets the current integration head. That is the snapshot users will receive—not the earlier branch tip the agent happened to edit.

  1. Capture main at C and build merge M from C plus the work branch.
  2. Inspect M in a detached worktree.
  3. Run semantic reviews and executable checks on M.
  4. Compare-and-swap main from C to M.
  5. If main is no longer C, stop; rebuild and verify again.
The rule: evidence may suggest, people or accepted authority decide, and landing verifies the exact result.
