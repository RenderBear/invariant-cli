1. The promise

Invariant is a repository-native memory and gate for agent-driven change. The memory preserves decisions that future work must know. The gate prevents a proposed change from landing until the relevant decisions have been considered and the exact prospective Git tree has been checked.

Design rule

Meaning remains prose. Invariant types identity, provenance, applicability, causal ground, authority, verification, and revision. It does not reduce an architectural argument to a closed taxonomy.

The operating philosophy: free-form agent reasoning for accuracy; deterministic, inspectable state where reasoning becomes consequential; near-zero user ceremony for routine work; and hard authority boundaries when an accepted promise is genuinely at risk.

Invariant is deliberately narrow. It is not a general knowledge graph, policy language, or workflow framework. A local host may organize repository folders and themed conversations, but that personal workspace is not repository memory or authority. Consequential work still enters the same Git-bound lifecycle.

2. Three public objects

The public model has three nouns. Everything else is either a specialization, a derived view, or change-local machinery.

Authoritative

Record

Accepted meaning that may govern future work: a responsibility, architectural decision, relied-on promise, or durable constraint.

Power
May constrain a Change.
Form
Thin typed envelope around canonical prose.
Non-authoritative

Evidence

A grounded observation: repository behavior, external guidance, an audit finding, a test result, or a review.

Power
May support or challenge a Record.
Form
Attributable content bound to source and ground.
Causal process

Change

One managed repository change, from a human request through isolated work, evidence collection, verification, and landing.

Power
May produce Evidence and propose Record changes.
Form
Strict internal state around one goal and Git ground.
Property Record Evidence Change
Standing Accepted and governing Observed and non-governing Active or completed work
Causal identity Repository history and canonical prose digest Source plus commit, tree, or external retrieval time Request, captured base, work tip, and proposed tree

3. Evidence and authority

Invariant expects meaning to be discovered from many places: source code, tests, history, production behavior, standards, searches, security guidance, and established best practices. Those inputs have different reliability, but they share one standing when first introduced: Evidence.

Sources

Repository state, tests, incidents, documentation, standards, searches, papers, vendor guidance, and model-assisted investigation.

Evidence

Invariant retains provenance, scope, causal ground, method, and the observation itself. Confidence may guide review but does not grant authority.

Decision

An agent or human acts only within configured authority and the current request. Contradiction or insufficient authority becomes one explicit Change requirement.

Records

Accepted meaning is written as canonical prose with retrieval, evidence, verifier, revisit, and supersession coordinates.

Minimal envelopes, open meaning

The following examples are conceptual, not direct CLI input. They show what the product must preserve without deciding what a proposition means.

Record envelope

record:
  id: processor-source-ownership
  body: docs/architecture.md#source-ownership
  accepted_by: user:task:import-processor#turn-3
  applies_to: [repo:services/processor]
  supported_by: [evidence:audit-20260907]
  revisit_on: [repo:.gitmodules]
  verifies: [test:checks/source-ownership.sh]
  supersedes: [processor-external-ownership]
  facets: {confidence: accepted}

Evidence envelope

evidence:
  id: audit-20260907
  kind: repository-audit
  source: repo:services/processor
  ground:
    commit: 8d2f...
    tree: 40ae...
  scope: [repo:services/processor]
  observation: >-
    Processor ownership is implicit in startup
    and recovery behavior.

Change envelope

task:
  id: restore-processor
  goal: Restore work after restart.
  base: commit:8d2f...
  state: awaiting-decision
  records: [record:source-ownership]
  evidence: [evidence:candidate-40ae]
  requirements:
    - Decide whether ownership meaning changes.

4. The change lifecycle

Humans ask for a change normally. The coding agent or harness drives a Change through one fixed lifecycle. Routine work moves through without ceremony; uncertainty appears only as an explicit requirement.

Two suspension points

A semantic integration may ask for clarification before implementation or require judgment after evidence for the proposed change exists. It cannot replace branch isolation, evidence collection, verification, or landing.

5. The semantic decision

Internal impact calculations may remain sophisticated. The public question is smaller: what must this Change do about accepted meaning before it can land?

6. Changes are plural because work is parallel

Change remains the singular object type. A repository may hold many Changes at once, and one end-to-end Change may contain several independently executable work items. The host keeps small, coupled work single and parallelizes only disjoint ready work. Parallelism is expressed through captured bases, dependencies, claims, and convergence order—not through another semantic tier.

7. Guarantees retained

Simplifying the public ontology does not simplify away the control guarantees. These remain mandatory mechanics.

Git object identity

Ground, proposed change, and landing are bound to exact commits and trees rather than mutable branch names or timestamps.

Isolated Changes

Linked worktrees let several agents work in one clone without moving the integration checkout.

Evidence before authority

Repository observations, searches, audits, tests, and model output cannot silently become accepted meaning.

Exact-tree verification

Reviews and executable checks apply to the prospective integrated result, not merely the earlier work branch.

Independent challenge where it matters

Governance rewrites and contract definitions need a human or a fresh second reviewer, while ordinary bounded work keeps its lighter path.

Compare-and-swap landing

The local target moves only if it still equals the captured head. The landing records its original parent and review provenance; concurrent movement forces reconstruction.

Recoverable failure

A failed check, conflict, missing decision, or stale proposed change leaves the target unchanged and Change work available.

Explicit authority

Agent authority covers only repository meaning within the request. It does not imply destructive or unbounded external permission.

Local landing before publication

Remote publication is separate, disabled by default, and cannot retroactively make a verified local landing ambiguous.

8. Where the machinery goes

The implementation uses precise internal types for domains, reach, boundary dispositions, lifecycle stages, command outcomes, and evidence. Simplification means giving each concept one home and exposing only the projection appropriate to the audience.

Existing term Public standing Implementation role
Domain Record view Retrieval coordinate for a stable responsibility.
Architecture Record body Canonical prose carrying rationale, consequences, and revision conditions.
Contract Verified Record A Record whose observable consequences select executable witnesses.
Constraint Record specialization Repository terminology or facets; not a parallel authority store.
Audit, finding, discovery Evidence Different capture and resolution behavior expressed by internal discriminated types.
Reach and impact Evidence Derived intersections that explain why Records may apply or require review.
Candidate review and verifier result Evidence Candidate-bound semantic and executable observations.
Candidate, assessment, receipt, action Change internals Typed persistence, suspension, resumption, and exact-tree bindings.
Plan and reservation Change coordination Derived or disposable mechanics for dependency order, ownership, and liveness.
Stage, outcome, assurance Change projections One state machine should derive these views rather than storing competing truths.
Project registration and conversation Personal workspace Host-local navigation and provider context; never repository authority or landing evidence.

Normal product surface

initialize
→ ask for a change
→ retrieve governing Records
→ work in an isolated Change
→ collect Evidence
→ pause only for a real unresolved decision
→ verify the exact tree
→ land locally

Diagnostic commands, raw schemas, proposed-state construction, cache inspection, and coordination primitives remain available as an advanced machine API. They do not define the vocabulary a human must learn.

Reader guidance

Use this explanatory model to understand the system. Use the machine specification when implementing, reviewing, or changing Invariant's protocol and safety behavior.

Invariant's core rule: Records state what must be preserved, Evidence states what was observed, and Changes bind action and judgment to the exact repository result.
